# LocalHelm UX review: know the next step, finish the action

Delivery update (2026-10-15): packets A–D below are now implemented and verified. See the [delivery tracker and acceptance contract](specs/ux-friction-packets.md) and the packet evidence in `appledger/records/evidence/`. The original findings and verification below describe the initial pass.

Assignment: a broad UXcalibur pass across LocalHelm, emphasizing both static friction (understanding what to do) and dynamic friction (getting stuck during an action). The additional published UXcalibur executable incident is included as concrete release-flow evidence. This is a source review plus isolated browser and regression verification, not measured user research.

## Diagnosis and design direction

LocalHelm already brings useful jobs together: inspect a workspace, commit changes, release packages, update dependents, deploy sites, and manage local services through companion plugins. Its compact fleet table and plan-before-write confirmations are worth preserving.

The main gap is continuity between **what needs attention**, **what can run now**, and **what actually completed**. A blocked release could vanish from the Publish view. The header could report All quiet while Today contained a blocker. Concurrent reads could discard valid updates, and an incomplete progress stream could return an empty success. A failed action could close its confirmation and leave a detached error at the top of the page.

The target experience is a dependable control panel: Today explains the next useful action or blocker; Fleet shows the source facts; confirmations identify the target and consequences; progress ends with an acknowledged result or explicit uncertainty; recovery refreshes facts before another write. Keep the nautical identity, dark HUD, compact rows, and restrained gold action emphasis. Teach the jobs in plain language instead of requiring familiarity with the metaphor.

## Findings and disposition

| ID / priority | Evidence and consequence | Change / status |
| --- | --- | --- |
| R1 / high — ambiguous npm target | `planPublishOne` targets the enrolled directory. UXcalibur had a separate generated package, so publishing the root shipped 184 development files with no executable. A matching registry version did not establish a usable release. | **Repaired in UXcalibur**: one root public manifest/version/README, executable declaration, prepack build, exact twelve-file whitelist verification, isolated install and npx execution. **LocalHelm improved**: local Publish confirmation now names package.json, README, and declared executable entries. Full artifact validation remains a follow-up below. |
| R2 / high — incomplete stream appeared successful | The previous dashboard reader returned `result ?? {}` at EOF, accepted a failed HTTP NDJSON response, and did not flush split UTF-8. An interrupted write could look finished. | **Implemented**: require a terminal result, handle split encoding, retain server errors, reject failed HTTP status, and explicitly require status reconciliation after interruption. A result acknowledgement completes without waiting for connection close. |
| R3 / high — independent refreshes lost results | One global status-read ticket discarded A when B started. A scoped read could also discard a broad read for unrelated subjects. | **Implemented**: per-subject request ordering, full/scoped merging, newest overlapping request wins, and status-read invalidation on board switch. Browser cases cover independent, same-row, and broad/row response order. |
| R4 / high — failed actions lost their context | Default `run()` closed the confirmation on failure. The original target and partial progress disappeared; stopped actions could retain a spent write button. | **Implemented for default confirmation flows**: retain target/progress/error, remove the obsolete write callback, and offer Close and refresh. Retrying requires a fresh plan. Publish/Land retain their existing specialized recovery flows. Reload durability for other job types remains a follow-up. |
| R5 / medium — Publish hid blocked releases | `rowHasNeed('publish')` included only eligible rows; disabled actions depended on hover tooltips. People seeking a release could get an empty list rather than the prerequisite. | **Implemented**: unpublished releases stay in the filter with visible recovery guidance. Bulk Publish still includes only eligible rows. Gold emphasis goes to the first enabled action even when a blocked Publish control precedes it. |
| R6 / medium — quiet state contradicted work | Header lamps counted eligible writes, while Today could contain blocked rows, site jobs, or port work. All quiet could appear before plugin reads finished. | **Implemented**: when there are no eligible-write lamps, unresolved Today work gets Review; loading and errors cannot be presented as All quiet. Quiet package-list copy is explicitly scoped to package/Git work. |
| R7 / medium — activity persistence impersonated action failure | The asynchronous activity POST wrote its error into the shared action-error state. A logging problem could replace an actionable failure or undermine a valid plan. | **Implemented**: persistence warnings belong in Activity with an unread indication; they do not overwrite the action's result/error. Durable buffering of unsaved activity remains a separate enhancement. |
| R8 / medium — command version was false | CLI `--version` printed the literal `0.0.0`. That makes installed-versus-checkout diagnosis unreliable. | **Implemented**: read the actual package manifest. Regression runs the CLI and compares its output with the manifest. |
| R9 / medium — guidance accumulated jargon and repetition | Today introduced “Looks,” “Ports facts,” and “missing site slip” before the user had a clear job. Fleet repeated a dense operation inventory above and below the table. Empty Ports said all listening even with zero leases. Mobile Fleet hid actions beyond the initial table viewport without a scrolling cue. | **Implemented**: short task-based introductions, plain description of Land, concise Fleet guidance, truthful empty-state copy, and a keyboard-focusable Fleet scroll region with a narrow-screen cue. The existing product vocabulary remains available in its relevant context. |
| R10 / high — default URL normalization could throw during startup | Browser checks loading `?tab=today` reached SvelteKit `replaceState` before its root was initialized (`$set` on undefined). | **Implemented**: enable URL synchronization after SvelteKit's navigation lifecycle, preserving the existing replace-only URL behavior. Verified by direct canonical/default-tab loads in the browser pass. |
| R11 / medium — a plugin engine column could crash FilePress rendering | The table adapter always prepended `engine`; a board already exposing that column produced duplicate keyed elements and a rendering exception. | **Implemented**: keep exactly one engine column. The synthetic board reproduces this case and the column regression covers it. |

These changes predict less confusion and safer recovery; they do not establish measured improvements in completion time, usability, or release success.

## Implementation packets (completed 2026-10-15)

### A. Verify the exact npm artifact before publishing

Priority: high. The manifest details now shown in the confirmation identify the source, but they do not prove that packed executable files exist or that the package is usable. Packages without `bin` can legitimately be libraries, so a global “must have an executable” rule would be wrong.

Own a generic artifact contract: package directory/version/README sources, lifecycle/build expectations, generated-target support when needed, and an explicit package-versus-CLI distinction. During confirmed apply, pack once, validate declared entry files and packed identity, and publish that same verified archive. Do not execute lifecycle scripts merely by opening a read-only plan. Show a concise artifact summary and expand for files. Check library, CLI, generated package, build failure, missing declared bin, stale version, and changed tree cases. Include GitHub workflow targets only with verified workflow support. Do not infer them from the repository name.

### B. Durable results for all multi-project actions

Priority: medium. Publish and Land already persist specialized snapshots. Other actions retain their failure result in this page but lose it on reload. Standardize a job identity, per-subject result, completed/pending/unknown states, and a read-only reconciliation path. Retry only freshly planned remaining work. Test partial completion, tab reload, server restart, lost acknowledgement, Stop, and a status-refresh failure after a successful write. A transport interruption must never imply rollback.

### C. Finish the shared action language and compact layout

Priority: medium. Use one glossary at decision points: Commit saves changes to Git; Push sends commits to origin; Publish releases an npm package; Ship deploys; Land updates and deploys a FilePress site. Keep technical commands in expanded plan details. Extend visible prerequisite guidance to blocked Push and companion actions. Consider moving the always-visible manual Bump column into a row action menu, since Publish already handles the common bump path; preserve explicit patch/minor/major control in its plan. Prototype before removing that control.

Keep the table's scan rhythm: one version comparison, one Git summary, one primary next action; secondary controls stay compact. Preserve the inline private marker instead of adding another row button. On phones, preserve a readable project identity and next step while keeping horizontal table scrolling inside its pane. Test a large fleet and long names, not just the small synthetic board.

### D. Companion failures and activity durability

Priority: medium. Review plugin read races and enabled/disabled transitions separately from status-read ordering, surface plugin-unavailable recovery at the affected pane, and distinguish not configured, loading, empty, and failed states. Buffer/retry unsaved activity without replacing acknowledged job results or dropping local entries when a later save completes. Verify fault isolation across several plugins and rapid Main/Demo switching. Current synthetic board rendering does not establish real companion command success.

## Verification

LocalHelm's own npm contract remains the repository root: `package.json` owns
the version and executable, and `README.md` is npm's README. Build with
`pnpm build` and `pnpm dashboard:build` before packing from that root;
`prepublishOnly` also runs those builds on publication. The public files are
the root allowlist (`bin`, `dist`, `dashboard`, license/notice/README, and the
logo). This pass does not introduce a generated release directory or alter
the fleet's enrollment.

The reliability batch passed nine targeted stream/order regressions, the dashboard build, zero Svelte check errors, and isolated browser checks for first run, independent/out-of-order reads, overlapping row reads, full/row merging, and interrupted stream recovery. The follow-up batch also corrects the reader's browser/Node type compatibility for the library compiler. Final checks passed **338 tests**, the compiled/source CLI version, both builds, and the expanded synthetic browser scenarios, including keyboard horizontal scrolling. The final session record retains counts and limits.

No npm publication, Git push, site deployment, real fleet action, provider/model call, or project phase transition was performed by this review. UXcalibur's corrected package is prepared for publication separately.
